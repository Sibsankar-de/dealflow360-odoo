# agents.md

## Purpose

This document defines the rules, responsibilities, and operating procedures for AI agents working on the DealFlow360 client application.

All agents must follow these instructions without exception.

---

## Project Scope

The client application is responsible for:

* User interface implementation
* User experience workflows
* State management
* API integration with backend services
* Authentication flows
* Dashboard visualization
* Deal management interfaces
* Quote and proposal interfaces
* Customer and account management screens
* Notification and activity interfaces
* Reporting and analytics views

Business logic, workflow enforcement, pricing calculations, and data validation must remain on the server whenever possible.

---

## Agent Responsibilities

Agents must:

* Maintain a clean and scalable frontend architecture
* Keep UI components reusable
* Follow existing project structure
* Maintain type safety
* Keep API integrations consistent
* Refer to AGENTS.md in the root directory for platform concepts, quotation lifecycles, and business rules
* Update architecture.md whenever required within the same task
* Update documentation when new modules are added
* Preserve backward compatibility unless explicitly instructed otherwise

Agents must not:

* Add unnecessary dependencies
* Introduce duplicate components
* Create unused code
* Leave TODO placeholders
* Leave mock implementations in production code
* Commit debugging code
* Generate AI attribution comments
* Generate decorative comments

---

## Documentation Rules

Whenever any of the following changes:

* Folder structure
* State architecture
* Routing architecture
* Shared component architecture
* API architecture
* Authentication architecture

The agent must update within the same task:

* architecture.md

Documentation must always reflect the latest implementation.

---

## Code Style Rules

### General

Use:

* Clear naming
* Consistent formatting
* Small focused components
* Predictable state flow

Avoid:

* Dead code
* Commented code blocks
* Temporary hacks
* Magic values

---

## Comments

Allowed comments:

* Business-critical explanations
* Complex implementation explanations
* Public API documentation

Do not write:

* AI generated comments
* Decorative comments
* Banner comments
* Emoji comments
* Progress comments

Examples of forbidden comments:

```ts
// Generated by AI

// Amazing utility function

// TODO later

// Quick fix
```

---

## Character Rules

Only standard keyboard characters are allowed inside:

* Source code comments
* Markdown files
* Documentation

Do not use:

* Emojis
* Unicode bullets
* Decorative separators
* Smart quotes

Forbidden examples:

```text
🚀
✅
❌
•
—
“
”
```

Use:

```text
-
*
"
'
```

---

## Component Guidelines

### Reusability First

Before creating a component:

1. Search existing components
2. Reuse if possible
3. Extend if necessary
4. Create new only when justified

### Component Structure

Each component should:

* Have a single responsibility
* Accept typed props
* Avoid business logic
* Remain independently testable

---

## State Management Rules

State must be categorized into:

### Server State

Examples:

* Deals
* Customers
* Quotes
* Activities
* Notifications

Use approved data fetching patterns.

### Client State

Examples:

* Modal visibility
* UI filters
* Form state
* Temporary selections

Avoid duplicating server state locally.

---

## API Integration Rules

All API communication must:

* Go through centralized API services
* Use typed request models
* Use typed response models
* Handle loading states
* Handle error states

Components must not directly call network clients.

---

## Routing Rules

Routes must be:

* Feature based
* Predictable
* Lazy loaded when appropriate

Avoid deeply nested route structures unless required by workflow.

---

## Form Rules

Forms must:

* Validate user input
* Display clear errors
* Prevent invalid submissions
* Handle loading states
* Handle retry scenarios

Validation logic should be shared whenever possible.

---

## UI Rules

The UI must:

* Remain responsive
* Support desktop-first workflows
* Maintain accessibility standards
* Preserve visual consistency
* Always use theme colors defined in globals.css
* Whenever a new color is needed, define it in globals.css and notify the user

Avoid introducing new patterns when an existing pattern already exists.

---

## Performance Rules

Agents should:

* Minimize unnecessary renders
* Lazy load large modules
* Memoize only when justified
* Optimize expensive calculations

Avoid premature optimization.

---

## File Organization Rules

Preferred structure:

```text
src/
├── app/
├── routes/
├── modules/
├── components/
├── services/
├── hooks/
├── store/
├── utils/
├── types/
└── assets/
```

Feature-specific code should remain inside its module whenever possible.

---

## Testing Rules

New functionality should include:

* Component tests where appropriate
* Integration tests for critical flows
* Regression protection for existing behavior

Avoid testing implementation details.

---

## Architecture Ownership

Agents are responsible for maintaining architectural consistency.

Before introducing:

* New state management patterns
* New routing patterns
* New UI frameworks
* New API layers

The impact on the overall architecture must be evaluated and documented.

---

## Completion Checklist

Before considering a task complete:

* Code compiles successfully
* Lint checks pass
* Type checks pass
* No unused imports
* No unused files
* Documentation updated
* architecture.md updated if required
* No AI comments present
* No non-keyboard characters present
* Existing functionality remains intact

Failure to satisfy any item means the task is not complete.
